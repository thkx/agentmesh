# M11 — Workflow Runtime Reliability Acceptance

M11 is an acceptance-only milestone. It adds no runtime feature or schema migration. Its purpose is to exercise the M7–M10 persistence, lease, fencing and idempotency contracts under real process boundaries.

## Acceptance matrix

| Scenario | Test | Required invariant |
|---|---|---|
| Multi-process claim race | `TestM11MultiProcessClaimAndSIGKILLRecovery` | Four independent OS processes contend for one queued run; exactly one obtains the lease |
| SIGKILL after claim | `TestM11MultiProcessClaimAndSIGKILLRecovery` | Killing the owner process leaves a recoverable lease; a later process claims after expiry |
| Old worker resumes | `TestWorkflowFencingRejectsStaleWorkerWrites` and process test | A prior fencing generation cannot write the checkpoint or complete a node |
| Third-party side effect | `TestM11ThirdPartySideEffectIsNotDuplicatedAfterAmbiguousCrash` | A durable `started` invocation is indeterminate and not replayed; provider idempotency key deduplicates repeated HTTP requests |
| Long-running node | `TestM11LongRunningNodeLeaseIsRenewedByWorkerHeartbeat` | Node runs beyond its initial lease while heartbeat renews both run and node leases; a contender cannot claim it |
| Existing concurrent claim | `TestM9ConcurrentWorkersOnlyOneClaimsJob` | Two concurrent claim attempts yield one winner |

## Run

Use the Go version declared by `go.mod` (Go 1.27.3) and run:

```bash
./scripts/reliability/m11.sh
```

The script runs race-enabled targeted tests, the full race-enabled suite and `go vet`. The multi-process SIGKILL test takes approximately 4–8 seconds, excluding test-binary compilation.

## Test design details

- The process test launches the current Go test binary four times. Each child opens the same SQLite WAL database independently, attempts a claim, writes its result to a separate file and then blocks. The parent verifies one winner, sends an OS kill signal to all children, waits for the lease timeout and claims with a newer fencing generation.
- The long-running node test holds a fake Agent call open beyond the 3-second lease horizon. A second claimant attempts to take the same run while the first worker's heartbeat is active.
- The third-party test uses an HTTP test server with a provider-style `Idempotency-Key`. It simulates the crash window after the remote side effect but before the local ledger completion. The ledger refuses to replay an ambiguous `started` invocation. A second pair of direct HTTP calls verifies the provider's idempotency contract.

## Production acceptance caveats

These tests establish process-level SQLite coordination on a shared filesystem and validate the code paths exercised. They do not prove multi-host SQLite safety on arbitrary network filesystems, provider idempotency for APIs that do not implement it, exactly-once side effects, or behavior under every kernel/filesystem failure. Run the suite on the actual deployment filesystem and provider sandbox before production rollout.
