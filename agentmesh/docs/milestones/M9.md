# M9 — Workflow Observability, History & Operator Recovery

M9 extends the M8 durable DAG runtime without replacing the M7 scheduler or changing the existing package layout.

## Delivered

- Append-only `workflow_events` stream with per-run monotonic sequence numbers.
- Run status and node status transitions are appended in the same SQLite transaction as `workflow_runs.state_json` updates.
- Worker claim, lease expiry, worker completion, recovery and operator actions are recorded.
- Event pagination (`after` + `limit`) and reconnectable Server-Sent Events (`Last-Event-ID`).
- Run history response combines the current run snapshot, event timeline and node observations.
- Node observations expose status, attempt count, worker owner, start/end timestamps, duration and error.
- Operator recovery can retry a failed node or skip a failed/interrupted node. An interrupted node cannot be retried automatically because its side-effect outcome is indeterminate. Condition nodes cannot be skipped because the selected branch cannot be inferred.
- Manual skip is explicitly marked and acts as a pass-through for downstream dependency resolution.
- Multi-connection SQLite race test ensures only one worker claims a queued job.
- Lease-expiry crash-injection test verifies recovery and corresponding history events.

## Migration

`000010_create_workflow_events.up.sql` creates the append-only event table and indexes. Existing M1–M8 migrations are unchanged.

## HTTP API

| Method | Path | Description |
|---|---|---|
| GET | `/api/v1/workflows/runs/:run_id/events?after=0&limit=100` | Incremental event history |
| GET | `/api/v1/workflows/runs/:run_id/events/stream?after=0` | SSE stream; reconnect with `Last-Event-ID` |
| GET | `/api/v1/workflows/runs/:run_id/history` | Run + events + node observations |
| GET | `/api/v1/workflows/runs/:run_id/nodes` | Node-level observations |
| POST | `/api/v1/workflows/runs/:run_id/nodes/:node_id/recover` | Operator retry/skip |

Recovery request:

```json
{
  "action": "retry",
  "comment": "Provider outage resolved; operator approved retry"
}
```

`action` is `retry` or `skip`. A retry is allowed only for a node in `failed` state. A node in `interrupted` state is not retried because an external side effect may already have happened. Retrying a failed Agent node is an explicit operator decision; verify provider/tool side effects first. Use `skip` only when an operator has reviewed the consequences. Condition nodes cannot be skipped.

## Event model

Events are immutable and ordered per run using `(run_id, sequence)`. Event append and run checkpoint updates use a single SQLite transaction in `SaveRun`. Worker claim/lease recovery and operator recovery events are written in the same transaction as their corresponding queue changes.

Clients should persist the last received sequence and request `after=<sequence>` after reconnecting. SSE connections are bounded to 30 seconds and should reconnect automatically.

## Operational notes

- SQLite WAL mode and a non-zero busy timeout are recommended for multiple local worker processes.
- Worker count may be increased with the existing `scheduler.workers` configuration; M7 Agent workers and M8/M9 Workflow workers are separate pools.
- Events may contain error strings and operational metadata. Do not place credentials, full prompts, or secrets in event payloads.
- This is durable at-least-once job delivery with idempotency/reconciliation safeguards, not a claim of exactly-once external side effects.
- Operator recovery is an audited control-plane action; production deployments should protect these routes with authentication and authorization before exposing them outside a trusted network.

New tests in `internal/workflow/checkpoint/sqlite_m9_test.go` cover concurrent worker claim exclusivity, expired lease recovery/event recording, and atomic operator retry. Existing runtime tests cover parallel fan-out/join and Agent snapshot reconciliation.
