# M15 — Reflection & Evidence-Grounded Learning

## Goal

M15 adds a bounded reflection stage after M14 Goal Outcome Evaluation. It converts one immutable Goal Evaluation plus the corresponding Workflow Run observations into a small set of reusable, evidence-grounded insights. Reflection is analysis only: it never mutates a Goal, Plan, Workflow Definition, Tool Policy, Agent Profile, or execution result.

## Flow

`Goal + Immutable Evaluation + Workflow Run Observations → LLM Reflection → Exact Evidence Validation → Append-only Reflection`

A reflection can be created only after an M14 evaluation exists for the same Goal and Run. This also allows reflection after the Goal has been completed; completed Goal state does not prevent post-run learning.

## Insight model

Each insight contains:

- `kind`: `success_pattern`, `failure_cause`, `improvement`, or `risk`.
- `title` and `description`.
- Optional `recommendation`.
- `confidence` in the inclusive range `[0,1]`.
- One or more exact evidence references `{node_id, quote}`.

The LLM is explicitly instructed to treat all supplied content as untrusted data, distinguish observed facts from hypotheses, and avoid inventing causes. The server verifies every node ID and quote against the actual Workflow Run. Quotes may refer to a node's output or error, allowing reflection on failed runs as well as successful ones. Exact quote validation proves source presence, not semantic truth or causality.

Evidence limits:

- Per-node output: 64 KiB.
- Combined node output and errors: 256 KiB.
- Serialized reflection input: 512 KiB.
- Model response: 128 KiB.
- Maximum 32 insights, 16 evidence items per insight.

An empty insight list is valid when no reusable lesson is supported by evidence; the reflection summary is still persisted.

## Persistence and idempotency

Migration `000015_goal_reflections` creates `goal_reflections`, uniquely keyed by `(goal_id, run_id)` and linked to the corresponding `goal_evaluations(goal_id, run_id)`. SQLite triggers reject UPDATE and DELETE to keep reflection records append-only. Repeated requests return the existing reflection without another model call once the record exists.

The unique constraint protects persistence under concurrent requests. There is no cross-process model-call reservation, so two simultaneous first-time requests may both incur model usage before one record wins the insert race.

## HTTP API

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/v1/goals/:id/reflections` | Create reflection for an evaluated Run; body `{"run_id":"...","model_id":"..."}` |
| `GET` | `/api/v1/goals/:id/reflections` | List reflections (`limit`, default 50, max 200) |
| `GET` | `/api/v1/goals/:id/reflections/:run_id` | Get immutable reflection for a Run |

Reflection may incur model usage charges. The evaluator model must be available in the existing Model Gateway.

## Non-goals

- Automatically triggering reflection when a Workflow Run completes.
- Updating Agent Profiles, prompts, Tool Policies, or Plans from a reflection.
- Long-term Memory retrieval/injection or cross-Goal knowledge sharing.
- Autonomous replanning, retry, or workflow mutation.
- Treating model confidence as calibrated probability or evidence as proof of causality.
