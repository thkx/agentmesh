# M12 — Goal & Planning Core

M12 introduces a durable goal model and structured planning core. It does not execute plans or compile them into Workflow definitions; those responsibilities are deferred to M13.

## Scope

- Goal domain: description, constraints, success criteria, context, lifecycle status.
- Goal management: create, update, get, list and cancel.
- Planner contract independent of the model provider.
- LLM Planner backed by the existing Model Gateway.
- Strict structured JSON parsing; unknown fields and trailing content are rejected.
- Plan validation: identifiers, supported step types, required Agent Profile, dependency references, duplicate dependencies and DAG cycle detection.
- Per-goal immutable Plan versions persisted in SQLite.
- HTTP API for Goal and Plan management.

## Data model

Migration `000012_create_goal_planning` adds:

- `agent_goals`: goal description, JSON constraints, success criteria, context, status and timestamps.
- `agent_plans`: immutable plan snapshots with a monotonically increasing per-goal version, objective, JSON steps, model ID and creation time.

Plan version allocation is performed in one SQLite statement using a CTE and `INSERT ... RETURNING`, with a unique `(goal_id, version)` constraint as a final guard.

## Plan contract

The planner returns an object with `objective` and `steps`. A step contains:

- `id`, `name`, `description`, `type`
- `dependencies`
- optional `agent_profile`, `input`, `retry_policy`

Supported step types are `agent`, `condition`, `approval`, and `end`. Agent steps require an `agent_profile`. Step IDs must match `^[a-zA-Z][a-zA-Z0-9_-]{0,63}$`. A plan may contain at most 128 steps. The dependency graph must be acyclic and every dependency must reference an existing step.

The Plan is treated as untrusted model output. Validation is deterministic and happens before persistence. No tools are executed by the Planner.

## HTTP API

All routes are under `/api/v1`:

| Method | Path | Description |
|---|---|---|
| `POST` | `/goals` | Create a Goal |
| `GET` | `/goals` | List Goals (`limit`, default 50, max 200) |
| `GET` | `/goals/:id` | Get a Goal |
| `PUT` | `/goals/:id` | Update an active Goal |
| `POST` | `/goals/:id/cancel` | Cancel an active Goal |
| `POST` | `/goals/:id/plans` | Generate and persist a Plan; body: `{"model_id":"..."}` |
| `GET` | `/goals/:id/plans` | List Plan versions (`limit`, default 50, max 200) |
| `GET` | `/goals/:id/plans/:version` | Get a specific Plan version |

A Plan-generation request calls the configured Model Gateway and may incur provider usage charges. M12 leaves `max_output_tokens` at the provider/model default unless a planner instance is explicitly configured with a positive limit; the returned JSON content is capped at 256 KiB. The model ID must exist in the AgentMesh model catalog and its Provider must be executable.

## Lifecycle and boundaries

- Goals are created as `active`; an active Goal may be updated or canceled.
- Canceling an already canceled Goal is idempotent.
- A canceled Goal cannot receive a new Plan.
- Plans are immutable snapshots. Generating another Plan creates the next version; it does not overwrite previous versions.
- M12 does not run Agent steps, invoke tools, create Workflow runs, or perform autonomous replanning.
- M12 does not yet implement Goal completion evaluation, Agent Profile matching, Reflection, or long-term Memory.
- The HTTP API inherits the existing unauthenticated/loopback-only security boundary.
