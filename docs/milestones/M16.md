# M16 — Memory System

## Objective

Add a durable, evidence-grounded memory layer that turns M15 reflections into reviewable candidates, supports explicit promotion/rejection/archive lifecycle, retrieves only active memories, and supplies retrieved context to M13 plan executions.

## Memory model

- **Episodic**: a specific experience tied to a Goal, Workflow Run, and M15 Reflection.
- **Semantic**: a reusable fact/pattern promoted after human or trusted application review.
- **Procedural**: a reusable method promoted after human or trusted application review.
- **Candidate**: imported from Reflection but not retrievable by Agents.
- **Active**: approved and retrievable.
- **Archived / Rejected**: retained for audit, excluded from retrieval.

M16 intentionally does not use an embedding service or vector database. Retrieval is deterministic lexical matching with confidence and recency tie-breaking, scoped to global, Goal, and Agent Profile memories. This keeps the first memory release local, inspectable, provider-independent, and easy to validate. An embedding index can be introduced later behind the retrieval interface if measurements justify it.

## APIs

- `POST /api/v1/goals/:id/memories/ingest` — import one M15 Reflection as candidates (`{"run_id":"..."}`).
- `GET /api/v1/goals/:id/memories` — list Goal memory records.
- `POST /api/v1/memories/:memory_id/promote` — explicitly approve and classify a candidate.
- `POST /api/v1/memories/:memory_id/reject` — reject a candidate with a reason.
- `POST /api/v1/memories/:memory_id/archive` — archive an active memory.
- `POST /api/v1/memories/search` — search active memory with optional Goal and Agent scopes.

Promotion request:

```json
{
  "type": "procedural",
  "scope_type": "global",
  "reason": "Reviewed the source evidence and confirmed this method is reusable."
}
```

## Execution integration

The M13 Plan Execution Service retrieves active memories separately for each Agent Profile before creating a new Workflow Run. It stores the bounded results in the reserved `_agentmesh_memory_by_profile` input map. At prompt-render time, the Runtime selects only the current Agent node’s bound profile, exposes that value as `_agentmesh_memory_context`, and removes the profile map from the rendered context. Retrieved memory is explicitly labeled as untrusted reference data, not instructions.

The existing run idempotency key is unchanged. Before retrieving memory, the bridge checks whether the deterministic Run already exists. On retry it reuses the persisted input snapshot and does not retrieve memory again. Thus later memory promotion or archival cannot mutate an already-created Run.

## Persistence and safety

Migration `000016_memory_system` adds `agent_memories`, source uniqueness, Goal/Reflection foreign keys, lifecycle checks, indexes, immutable source fields, and no-delete retention. Migration `000017_memory_source_integrity` additionally verifies that `source_reflection_id`, `goal_id`, and `source_run_id` identify the same Reflection row; the composite Goal/Run foreign key alone did not guarantee this denormalized ID matched. Candidate promotion, candidate rejection, and active archival are the only lifecycle transitions. Retrieval updates access timestamps/counters but does not modify memory content.

## Deliberate limitations

- Reflection ingestion is explicit; M16 does not silently promote or auto-ingest all reflections.
- Promotion is an explicit API action with a mandatory reason; no LLM self-approval. The current HTTP layer has no user identity/audit principal, so this is an explicit operator action within the existing trusted API boundary, not cryptographic proof of who approved it.
- Retrieval is lexical, not vector/semantic embedding search. The repository currently caps the candidate set at 500 before application-level lexical ranking; this is an MVP bound, not a guarantee of globally optimal ranking at larger memory volumes.
- No automatic consolidation, contradiction resolution, forgetting policy, or cross-Goal deduplication yet.
- Agent-scoped memories are retrieved for the profile bound to each Plan Agent step. M16 adds an optional `agent_profile` field to the persisted Workflow Agent configuration; the Runtime selects only that profile’s memory context when rendering that Agent node prompt, so one profile’s private memory is not injected into another profile’s prompt.
- Memory APIs inherit the existing HTTP security boundary; deploy behind the configured trusted local boundary until authentication/authorization is added.

## Verification

The repository tests cover SQLite persistence, candidate idempotency, lifecycle transitions, Global/Goal/Agent scope isolation, rejected/archived exclusion, access counters, concurrent promotion, source-reflection consistency, and the M13 persisted memory snapshot retry path. The Runtime test verifies that a rendered Agent receives only its bound profile’s memory context.
