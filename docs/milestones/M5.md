# M5 — Agent Runtime

## Scope

M5 adds a model-agnostic, application-owned Agent Loop on top of the existing ModelGateway and Tool Engine. It does not replace or reimplement the internal loops of Claude Code, Codex, Gemini CLI, or OpenCode adapters from M3.

## Architecture

- `internal/domain/agent`: task input, status, result.
- `internal/agent/runtime`: bounded execution loop, task lifecycle, cancellation, concurrency limit.
- `internal/agent/contextmanager`: deterministic character-budget trimming; character counts are not represented as token counts.
- `internal/agent/loopguard`: step/tool-call budgets and repeated-call detection.
- `internal/transport/http/handlers/agent.go`: HTTP run/get/cancel endpoints.

The Runtime depends on two narrow interfaces: `Model.Generate` and `ToolCaller`. The production Model is the existing `modelgateway.Gateway`; ToolCaller is the existing `tools.Engine`.

## Model control protocol

Because the current ModelGateway request/response contract does not yet expose native cross-provider tool-call blocks, M5 uses an explicit JSON control envelope in assistant text:

```json
{"type":"tool_call","tool":"file.read","arguments":{"path":"README.md"}}
```

or

```json
{"type":"final","content":"The task is complete."}
```

This protocol is deliberately isolated in the Agent Runtime. Tool results are appended as user-role messages with a `tool:<name>` label because the existing OpenAI, Anthropic, and Gemini adapters do not yet accept native tool-result message blocks. M6 can add native provider tool-call normalization without changing the task domain or scheduler contracts.

## Safety

- Tool invocation is always routed through the existing Tool Engine and its Policy.
- `approved_tools` is an explicit per-task allowlist of tool names pre-approved by the caller; it does not bypass command allowlists or other Tool Engine checks.
- Read/write/execute permissions remain enforced by the configured Tool Policy.
- Maximum steps, tool calls, context characters, concurrent runs, and per-task timeout (default 15 minutes, maximum configured value one hour) are bounded. Task-level step/tool-call/timeout values may lower configured limits but cannot raise them.
- Repeated identical tool calls are blocked after two attempts.
- Cancellation propagates through model and tool contexts.
- HTTP remains loopback-only because the API has no authentication.

## HTTP API

- `POST /api/v1/agents/run`
- `GET /api/v1/agents/tasks/:id`
- `POST /api/v1/agents/tasks/:id/cancel`

Example request:

```json
{
  "id": "task-001",
  "model_id": "gpt-4.1",
  "workspace_id": "demo-run",
  "prompt": "Read README.md and summarize the project",
  "max_steps": 8,
  "max_tool_calls": 5,
  "timeout_seconds": 600,
  "approved_tools": []
}
```

`max_steps`, `max_tool_calls`, and `timeout_seconds` can only reduce the configured limits. `approved_tools` is an explicit list of tool names pre-approved for this task; keep it empty unless the caller intentionally authorizes write/execute tools.

`POST /run` executes synchronously and returns the terminal result. The in-memory task registry supports status lookup and cancellation while a run is active. Task persistence and durable asynchronous scheduling are out of scope for M5.

## Known limitations

- Native function/tool calling is not yet normalized across provider SDKs; M5 uses the JSON control protocol.
- Context trimming uses a character budget, not tokenizer-accurate token accounting.
- Task state is in-memory and is lost on process restart.
- The Runtime does not create or own workspaces; callers supply an existing managed Workspace ID.
- The Runtime does not run CLI coding agents inside its own loop. M3 CLI adapters retain their own agent execution behavior.
