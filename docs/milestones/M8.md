# M8 — Durable Agent Workflow / Graph Runtime

## Scope

M8 adds a versioned graph workflow layer above the existing M7 Agent Runtime and SQLite Scheduler. It does not replace the M7 scheduler, agent runtime, provider adapters, or tool ledger.

## Implemented

- Versioned workflow definitions persisted in SQLite (`workflows`).
- Workflow run snapshots persisted in SQLite (`workflow_runs`).
- Graph compiler validates node IDs/types/configuration, edge references, entry node, reachability, end nodes, conditional true/false edges, and rejects cycles.
- Runtime supports agent, condition, approval, and end nodes.
- Agent nodes call the existing Agent Runtime with node-specific model, workspace, prompt, limits, and approved tools. Different nodes can therefore use different models and tool allowlists.
- Condition nodes compare a context value (dot-path supported) with a configured JSON value and route on `true` / `false` edges.
- Approval nodes persist `waiting_approval`; approve continues from the next node, reject ends the run as `rejected`.
- A node's running state is checkpointed before execution and its output/status is saved after execution.
- Durable Workflow Worker queue (`workflow_jobs`) with atomic SQLite claims, owner-bound leases, heartbeats, bounded lease recovery, graceful shutdown, and retry of runs that expired before a node began.
- Node-level idempotency ledger (`workflow_node_executions`) stores a deterministic `(run_id,node_id)` key before node execution and a durable output afterward. A completed node output is reconciled after a crash-before-run-checkpoint.
- Agent-node recovery consults the persisted Agent Runtime result using the deterministic Agent task ID. Succeeded snapshots are reconciled; failed snapshots with zero tool calls can be safely retried; unknown outcomes or possible side effects become `interrupted` and are never blindly replayed.
- Graph supports DAG parallel fan-out and join. Independent ready nodes execute concurrently (bounded to 8 per Workflow run); join nodes wait until all incoming predecessors resolve. Conditional edges activate only the selected branch and propagate skipped nodes.
- Workflow start and approval continuation are enqueued and return immediately; worker execution is independent of the HTTP request lifecycle.
- Workflow policy is injected through a `Policy` interface. Default bootstrap policy is `AllowAll`; deployments should replace it with a restrictive implementation before exposing the API.
- Capability registry supports reusable `ToolSet` capabilities that inject approved tool allowlists and prompt context into Agent nodes; custom capabilities can implement the same interface and be installed through `Engine.SetCapabilities`.
- HTTP APIs expose definition save/read, run start/read/list, and approval/rejection.

## API

- `PUT /api/v1/workflows/:id`
- `GET /api/v1/workflows/:id?version=N`
- `POST /api/v1/workflows/:id/runs` (durable enqueue; returns `202` with a queued run)
- `GET /api/v1/workflows/:id/runs`
- `GET /api/v1/workflows/runs/:run_id`
- `POST /api/v1/workflows/runs/:run_id/approve`
- `POST /api/v1/workflows/runs/:run_id/reject`

## Example definition

```json
{
  "id": "code-review",
  "name": "Code review workflow",
  "version": 1,
  "entry": "review",
  "nodes": [
    {"id":"review","type":"agent","agent":{"model_id":"gpt-model","workspace_id":"default","prompt":"Review this change"}},
    {"id":"approval","type":"approval","approval":{"message":"Approve the proposed changes?"}},
    {"id":"done","type":"end"}
  ],
  "edges": [
    {"from":"review","to":"approval"},
    {"from":"approval","to":"done"}
  ]
}
```

Run with `POST /api/v1/workflows/code-review/runs` and body `{"input":{"change":"..."}}`. The API immediately returns `202` with status `queued`; poll `GET /api/v1/workflows/runs/:run_id`. When the run reaches the approval node its status becomes `waiting_approval`. Approve with `POST /api/v1/workflows/runs/:run_id/approve`; the decision is persisted and the continuation is re-enqueued.

## Delivery and recovery semantics

- Definitions are versioned and runs pin the exact definition version.
- Run and node transitions are durable SQLite snapshots.
- Approval waits survive process restarts because the approval state is persisted; approval continuation is durably re-enqueued.
- Workflow jobs use owner-bound leases. An expired job with no active node can be requeued within the configured attempt limit.
- Node execution keys are deterministic (`run_id:node_id`). Completed outputs are replayed from the ledger rather than re-running the node.
- Agent task IDs are deterministic hashes of workflow run ID and node ID. Recovery reconciles succeeded Agent Runtime snapshots and safely retries only failed snapshots with zero tool calls (or tasks that never started).
- If an Agent snapshot is still running, has tool calls, or otherwise has an unknown outcome, the node is marked `interrupted`; automatic replay is refused. This is deliberate at-most-once protection, not a claim of exactly-once external side effects.
- Graph cycles remain rejected. Parallelism is DAG fan-out/join; loops and dynamically generated graphs are not part of M8.

## M8.1 implementation additions

Migration `000009_create_workflow_execution` adds:

- `workflow_jobs`: durable queue, attempts, availability time, lease owner and lease deadline.
- `workflow_node_executions`: unique node execution key, execution status, output, owner and lease metadata.

The Workflow Worker starts alongside the existing M7 Scheduler workers (worker count, poll interval, lease duration, and maximum attempts reuse the `scheduler` configuration) and is stopped before SQLite closes. Workflow API start/approval requests only persist state and enqueue work; they do not hold the HTTP connection for the model execution duration. Queue reconciliation repairs the crash window between persisting a queued run and creating/re-arming its queue row.
