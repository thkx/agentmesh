# M14 — Goal Outcome Evaluation & Completion

## Scope

M14 closes the Goal lifecycle after M12 Goal/Plan creation and M13 Plan execution. It evaluates a terminal Workflow Run against the Goal's immutable-at-evaluation success criteria, stores an append-only evaluation, and atomically marks the Goal completed only when the Workflow Run succeeded and every required criterion is satisfied with verifiable evidence.

## Flow

`Goal + PlanExecution + Terminal Workflow Run → Evidence Collection → LLM Evaluation → Evidence Validation → Append-only Evaluation → Goal Completion`

The evaluator does not execute tools, change Workflow Run state, modify a Plan, or replan. A Workflow Run being `succeeded` is necessary but not sufficient for Goal completion.

## Evidence policy

- Only output from `NodeSucceeded` nodes is supplied to the evaluator.
- Per-node output is capped at 64 KiB and total evidence at 256 KiB.
- Every evidence item must cite a real node ID and an exact substring of that node's output.
- A `satisfied` criterion must include at least one verified evidence item.
- The evaluator must return exactly one result for every Goal success criterion.
- Failed, rejected, or canceled Workflow Runs may be evaluated for audit, but their overall Goal evaluation is `inconclusive` and cannot complete the Goal.
- At least one required success criterion must exist for automatic completion.

The LLM's semantic judgment is not a cryptographic proof. Exact quote validation prevents fabricated source references but does not independently prove that the quote logically satisfies a criterion.

## Lifecycle

Migration `000014_goal_evaluations` adds `agent_goals.completed_at` and append-only `goal_evaluations`. The original `agent_goals.status` CHECK constraint is preserved (`active`/`canceled`); the API/domain derives `completed` when `completed_at > 0`. This avoids rebuilding a referenced SQLite table.

Evaluation insert and Goal completion update occur in one SQLite transaction. A unique `(goal_id, run_id)` constraint makes repeated evaluation requests idempotent. Completed Goals cannot be edited, canceled, planned, or started again. Existing evaluations can still be fetched after completion.

## API

| Method | Path | Description |
|---|---|---|
| `POST` | `/api/v1/goals/:id/evaluations` | Evaluate a terminal linked Run; body `{"run_id":"...","model_id":"..."}` |
| `GET` | `/api/v1/goals/:id/evaluations` | List evaluations (`limit`, default 50, max 200) |
| `GET` | `/api/v1/goals/:id/evaluations/:run_id` | Get the immutable evaluation for a Run |

The Run must be linked to the Goal by a M13 `plan_executions` record. The evaluator model must be enabled in the existing Model Gateway. Evaluation may incur provider usage charges.

## Non-goals

- Automatic evaluation scheduling on Workflow completion.
- Automatic retry of evaluator model calls.
- Reflection, long-term memory, or autonomous replanning.
- Changing workflow state based on Goal evaluation.
- Treating an LLM verdict as independent proof of external-world facts.
